# 网球小球检测器微调项目：需求规格

- 状态：Draft / 待确认
- 项目代号：`tennis-small-ball-detector`
- 创建日期：2026-08-02
- 生产目标：15 FPS 输出、每 5 帧刷新一次 Swing 分析

## 1. 背景与基线

当前 `yolo26n.mlpackage` 是以 COCO 训练的 80 类 YOLO26n Core ML 模型，输入尺寸为
640×640。运行时使用 `sports ball`（类别 32）检测网球，使用 `tennis racket`
（类别 38）检测球拍。

在 `rtsp://127.0.0.1:8554/16-10` 的 250 帧复核中，最终管线输出网球 59 帧
（23.6%）和球拍 38 帧（15.2%）。该结果混合了模型检测、标记恢复、轨迹选择和
静止球过滤，不能作为纯模型 Recall；项目必须首先建立像素级人工真值和纯模型基线。

1440p 画面缩放到 640×640 后，远处网球通常只剩少量像素。COCO 的通用
`sports ball` 特征不足以稳定覆盖远距离、运动模糊、镜面反射和室内复杂背景。

## 2. 项目目标

1. 在现有真实机位上提高可见网球的逐帧检测召回率，尤其是触球前后的小目标。
2. 保持球拍检测能力，继续使用一次统一目标检测推理，不新增常驻第二模型。
3. 保持主球选择职责在 `BallTrackSelector`：检测器负责发现所有实体网球，轨迹层负责选择主球。
4. 产出可追溯、可回滚的 PyTorch 权重、Core ML 模型、数据集版本和评估报告。
5. 在目标 Mac/ANE 上维持至少 15 FPS 的实时处理能力。
6. 支持人工在浏览器完成校准、下载 JSON，随后在本地从断点继续数据集、训练、导出和 RTSP 验证流程。

## 2.1 用户故事

- 作为人工复核员，我希望在报告页逐帧修正网球和球拍框，并随时下载标注，避免浏览器刷新或关闭后丢失工作。
- 作为模型训练人员，我希望把下载的标注 JSON 导入一个固定项目工作区，由工具验证来源并生成 YOLO 数据集，而不用手工改文件名或坐标。
- 作为项目负责人，我希望看到当前 workflow 阶段、阻塞原因、数据版本和模型版本，并能够从最后一个成功阶段继续。
- 作为运行维护人员，我希望新模型灰度失败时可以立即切回旧模型，不影响现有实时 Coach。

## 3. 推荐的模型范围

本项目推荐从官方预训练 `yolo26n.pt` 迁移学习为两类检测器：

```yaml
names:
  0: tennis_ball
  1: tennis_racket
```

不推荐只训练单类小球并与旧模型并行运行，因为这会增加一次完整推理；也不推荐继续
保留 80 类输出，因为网球场数据不会完整标注其余 78 类，容易把未标注对象当作负样本。

## 4. 标注规则

### 4.1 网球

- 标注每一个可人工确认的实体网球，包括主球、地面静止球和非主球。
- 边界框紧贴可见球体或运动模糊主体，不把轨迹尾迹包含在框内。
- 严重模糊但中心仍可可靠确认时允许标注；无法区分网球、灯光反射或标记点时不标注。
- 镜中真实反射单独标注为网球，由运行时镜像抑制和轨迹连续性选择主球。
- 程序绘制的圆圈、彩色点、文字和球拍框不得作为网球真值。

### 4.2 球拍

- 标注每个可确认的实体球拍，框覆盖拍头与拍柄的可见范围。
- 镜中球拍应标注，主拍仍由运行时连续性和位置规则选择。
- 程序绘制的球拍框不作为球拍真值。

### 4.3 负样本

- 必须保留不含网球的帧及困难负样本：鞋、灯光反射、黄色标识、时间戳、网线、地面纹理和程序叠加标记。
- 无目标帧必须有空标签文件，不能因“没有框”而从数据集中删除。

## 5. 数据集要求

### R1 — 数据来源隔离

当构建数据集时，系统应按视频会话而不是相邻帧随机划分 train、val、test，避免同一段连续画面泄漏到多个集合。

### R2 — 场景覆盖

当数据集进入首轮训练时，系统应至少覆盖当前两个本地 RTSP 源、干净原视频、已叠加标记视频、不同球员位置、运动模糊、镜面反射和无球困难负样本。

### R3 — 数据规模

当开始首轮候选模型训练时，数据集应至少包含 2,000 个已审核帧；其中独立测试集至少包含 400 帧，并至少来自两个未参与训练的视频会话。

### R4 — 小目标分层

当生成数据报告时，系统应按原图中球框的长边划分 `<8 px`、`8–15 px`、`16–31 px`、`>=32 px` 四档，并分别报告数量与 Recall。

### R5 — 标注质检

当数据版本被冻结时，系统应完成 100% 自动格式检查、至少 20% 双人复核，并记录漏标、错标、框偏移和叠加标记误标率。

## 5.1 人工校准与离线续跑

当前页面导出的 `swing_manual_annotations_v2` 是事件级真值，只包含挥拍边界、触球帧、
挥拍类型和复核状态。它继续用于 Swing 事件评估，但不能替代 YOLO 所需的逐帧边界框标注。

本项目新增独立的 `tennis_detection_annotations_v1` 检测真值，至少包含：

- `task_id`、`session_id`、源视频或证据包引用及 SHA-256；
- 原图宽高、FPS、帧号和时间戳；
- 每帧的 `tennis_ball` / `tennis_racket` 边界框；
- 可见性、遮挡、困难样本、人工确认状态和备注；
- 整段复核完成状态、导出时间和 schema 版本。

### R5.1 — 双真值分工

当人工下载 `swing_manual_annotations_v2` 时，workflow 应仅将其用于 Swing 事件 Precision、Recall、F1 和边界误差评估，不得将事件帧号伪装成 YOLO 边界框标签。

### R5.2 — 检测标注编辑器

当人工进入小球检测校准模式时，页面应支持逐帧播放和定位、创建/移动/缩放/删除网球或球拍框、标记无目标困难负样本，以及查看模型原始框但不把原始框自动视为人工真值。

### R5.3 — 浏览器持久化

当人工修改任意检测标注时，页面应保存到当前任务专属的浏览器存储；当页面刷新或重新打开时，应恢复相同帧和标注内容。

### R5.4 — 导入导出往返

当人工下载并再次导入 `tennis_detection_annotations_v1.json` 时，页面应无损恢复全部框、状态和备注；重复导入同一 `task_id` 不得产生重复标注。

### R5.5 — RTSP 像素留存

当标注任务来源是 RTSP 时，系统应在任务生成阶段保存被抽样的原始帧或可校验的本地视频片段；后续 workflow 不得依赖 RTSP 地址仍然可访问。仅有标注 JSON 而没有对应像素证据时，导入应失败并说明缺失文件。

### R5.6 — 人工下载后的导入入口

当用户把下载的事件或检测标注 JSON 交给 workflow 时，系统应提供一个本地命令入口，自动识别 schema、处理文件名中的空格或 `(2)` 后缀，并将文件复制到版本化工作区。

建议入口形式：

```bash
python3 tennis_detector_workflow.py ingest \
  --annotations "/Users/name/Downloads/tennis_detection_annotations_v1 (2).json" \
  --task-dir "/path/to/annotation-task"
```

### R5.7 — 导入校验

当标注被导入时，系统应在写入数据集前检查 schema、任务与会话 ID、源文件哈希、帧范围、类别、边界框范围、重复 ID 和未完成复核项；校验失败不得留下半成品数据版本。

### R5.8 — 自动续跑

当检测标注通过校验时，workflow 应依次执行或排队执行“提取帧 → 生成 YOLO 标签 → 数据质检 → 会话级切分 → 冻结数据版本 → 基线评估”，并在需要 GPU 训练前明确停靠。

### R5.9 — 断点状态

当 workflow 任一阶段完成或失败时，系统应原子更新状态清单，记录输入哈希、输出文件和错误；再次运行 `resume` 时应从最后一个成功阶段继续，而不是重复已完成阶段。

### R5.10 — 人工训练闸门

当数据集仍有 `needs_review`、缺少像素证据或质检未通过时，workflow 应阻止训练；当数据集满足冻结条件时，系统应显示可训练的数据版本和下一条命令。

### R5.11 — 事件标注兼容

当导入现有 `swing_manual_annotations_v2` 时，workflow 应调用现有 `swing_evaluation.py` 生成评估 JSON，并允许重新生成报告；该兼容路径不得要求用户重新做已经完成的事件标注。

## 6. 训练与实验要求

### R6 — 基线先行

在微调模型之前，评估程序应使用当前 `yolo26n.mlpackage` 和同源 PyTorch 权重在固定 test 集上记录 Precision、Recall、mAP50、mAP50-95、小球分档 Recall、误检/帧和推理耗时。

### R7 — 可复现实验

当执行训练时，系统应保存数据版本、Ultralytics 版本、基础权重、随机种子、图像尺寸、增强参数、训练参数、Git 提交和最佳 checkpoint。

### R8 — 小目标实验矩阵

当进入模型选择阶段时，系统应至少对比 640、960、1280 三种输入尺寸，并对比全帧训练与保持上下文的切片训练；不得仅依据训练集 loss 选型。

### R9 — 增强边界

当配置增强时，系统应验证 Mosaic、缩放、亮度、运动模糊和压缩伪影对独立 test 集的影响；任何增强不得把程序标记合成为真实网球。

### R10 — 类别接口

当候选模型改为两类输出时，运行时应从配置或模型元数据读取 `tennis_ball` 与 `tennis_racket` 类别，不再依赖硬编码的 COCO 类别 32/38。

## 7. 验收标准

### R11 — 检测质量

当候选模型在冻结 test 集上评估时，应同时满足：

- `tennis_ball` Precision ≥ 0.90；
- `tennis_ball` Recall ≥ 0.80；
- 8–15 px 网球 Recall ≥ 0.70；
- 困难负样本误检率 ≤ 0.05 次/帧；
- `tennis_racket` Recall 相对当前基线下降不超过 2 个百分点。

### R12 — 产品指标

当候选模型回放人工审核会话时，Swing 事件内网球覆盖率中位数应达到 0.70，触球窗口（候选帧前后各 3 帧）至少 60% 的事件应具有网球证据。

### R13 — Core ML 一致性

当 PyTorch 候选模型导出为 Core ML 后，Core ML 的网球 Recall 相对 PyTorch 下降不得超过 2 个百分点，且不得出现类别映射或坐标缩放错误。

### R14 — 实时性能

当 Core ML 候选模型在目标 Mac、ANE、1440p RTSP 源上运行 1,500 帧时，完整管线应稳定达到至少 15 FPS，丢帧和重连指标应被记录，分析间隔保持 5 帧。

### R15 — 回归安全

当候选模型进入灰度验证时，实时事件区间应保持不重叠，姿态、球拍、Local Coach 和 DeepSeek 旁路不得因模型切换而失效。

### R16 — 可回滚发布

当发布新模型时，系统应保留旧 Core ML 模型，通过版本化路径和配置开关切换；未经测试不得直接覆盖根目录的 `yolo26n.mlpackage`。

## 8. 交付物

- 版本化 YOLO 数据集及数据卡；
- 检测标注任务包、浏览器逐帧校准页和 `tennis_detection_annotations_v1` schema；
- `tennis_detector_workflow.py` 的 `ingest`、`status`、`resume` 命令及原子状态清单；
- 标注规范、质检报告和 train/val/test 会话清单；
- 当前模型纯检测基线报告；
- 训练配置、实验记录、`best.pt`；
- FP16 与 INT8 Core ML 候选模型及一致性报告；
- RTSP 回放、延迟、15 FPS 稳定性和 Coach 产品指标报告；
- 模型版本清单、灰度配置和回滚说明。

## 9. 非目标

- 本项目不修复姿态 ROI 过滤问题；
- 不重写 Swing 事件分段或 Coach 规则；
- 不把“主球/静止球”训练成帧级检测类别；
- 不使用程序绘制圆圈替代真实网球标注；
- 首轮不引入 TrackNet、Transformer 跟踪器或第二个常驻检测模型。

## 10. 官方依据

- Ultralytics 训练模式：<https://docs.ultralytics.com/modes/train>
- YOLO 检测数据格式：<https://docs.ultralytics.com/datasets/detect>
- 小目标切片与评估建议：<https://docs.ultralytics.com/guides/model-evaluation-insights>
- YOLO26 Core ML 导出：<https://docs.ultralytics.com/integrations/coreml>

官方流程支持从预训练权重进行自定义训练、使用 YOLO 格式的数据集，并在训练后执行
验证和 Core ML 导出。YOLO26 的 Core ML 导出不需要额外嵌入 NMS；候选模型仍需在
Mac 上对实际导出包重新验证。首轮建议先验证 FP16，再评估 INT8 的速度与 Recall 变化。
